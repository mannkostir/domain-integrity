# eslint-plugin-ddd-guard v0.1 — Design

Date: 2026-09-30
Status: Superseded by 2026-09-30-domain-integrity-v0.1-design.md (kept as fallback)

## 1. Purpose

Architecture guardrails for Domain-Driven Design codebases whose code is increasingly written by coding agents.

Agents produce code that passes tests but erodes architecture: domain files import the framework, modules reach into each other's internals, aggregates get mutated from outside. `eslint-plugin-ddd-guard` turns those violations into lint errors that agents already read and act on, and ships fix guidance written for agents.

### Goals

- Minimum: a portfolio-grade open-source project demonstrating DDD and agentic-workflow expertise.
- Ideal: adopted by NestJS/TypeScript teams on existing (brownfield) codebases.

### Success criteria

- A user installs the plugin on an existing NestJS repo with a conventional layout and gets meaningful results with zero configuration.
- On the three real-world validation repos, false positives are near zero after tuning.
- A recorded demo shows an agent correcting its own architectural violations using the lint output and rule docs.

### Non-goals for v0.1

- Reference application, code generators, MCP server, Claude Code hooks.
- Autofixes.
- Legacy `.eslintrc` configuration.
- Frameworks other than NestJS as a tested target (the domain rules are framework-agnostic, but only NestJS layouts are validated).

## 2. Context and prior art

- `Sairyss/domain-driven-hexagon` (~14.5k stars) dominates the NestJS DDD learning space; the project deliberately does not compete as an example repo.
- DDD building-block libraries (`@nestjslatam/ddd-lib`, `noddde`, Emmett) and outbox libraries are fragmented and ORM-bound; not competing there.
- DDD agent skills exist only as prose guidance, with no enforcement.
- `eslint-plugin-ddd` exists on npm with a single `require-spec-file` rule; no overlap.
- Generic boundary tools (`dependency-cruiser`, `eslint-plugin-boundaries`) enforce imports but have no DDD semantics (aggregates, value objects) and no preset DDD layout.

The project is a clean-room implementation. The private `modular-monolith-ddd-example` repo is used only as a reference and as the first real-world validation target; none of its code is copied.

## 3. Technical baseline

- ESLint 9 flat config only.
- typescript-eslint v8, TypeScript 5+, Node 20+.
- Single npm package; docs and `init` CLI ship inside it.
- Package name: `eslint-plugin-ddd-guard` (available on npm as of 2026-09-30).

## 4. Architecture

```
src/
  layout/        options + defaults → ProjectLayout      (pure)
  classify/      file path → { module, layer } | unknown  (pure)
  resolve/       import specifier → target file or package
  rules/         one file per rule
  configs/       recommended and strict presets
  cli/init       project inspection and agent-instruction writer
docs/rules/*.md  canonical explanation and fix guidance per rule
```

### 4.1 `layout`

Merges user options with defaults into an immutable `ProjectLayout`: module roots, layer globs, shared-kernel globs, public-entry-point globs, aggregate/entity/value-object detection settings.

Default module roots: `src/modules/*`, `src/domains/*`, `src/contexts/*`.

Default layer globs, relative to a module root:

| Layer | Globs |
|---|---|
| domain | `domain/**` |
| application | `application/**`, `commands/**`, `queries/**`, `use-cases/**` |
| infrastructure | `infrastructure/**`, `persistence/**`, `adapters/**` |
| presentation | `presentation/**`, `controllers/**`, `http/**` |

Default shared kernel: `src/lib/**`, `src/shared/**`, `src/common/**`.

User overrides replace the corresponding default entirely; they are not merged glob-by-glob.

Example:

```js
import dddGuard from 'eslint-plugin-ddd-guard';

export default [
  dddGuard.configs.recommended({
    modules: 'src/domains/*',
    layers: {
      domain: 'domain/**',
      application: ['commands/**', 'queries/**'],
      infrastructure: 'persistence/**',
    },
  }),
];
```

Invalid options (unknown keys, empty globs, a layer name outside the supported set) throw a descriptive error when the config is built, not at lint time.

### 4.2 `classify`

Pure function `classify(filePath, layout)` returning one of:

- `{ kind: 'layered', module, layer }` — inside a module and matching a layer glob;
- `{ kind: 'module-unlayered', module }` — inside a module but matching no layer glob;
- `{ kind: 'shared' }` — inside the shared kernel;
- `{ kind: 'unmapped' }` — anywhere else.

`module-boundaries` uses `module` from the first two kinds; `layer-dependencies` acts only on `layered`.

Core principle: **unknown means no opinion**. A file that cannot be classified is never the subject of a violation, and an import into an unclassified file is never a violation. This is the primary false-positive defense on brownfield codebases.

### 4.3 `resolve`

Resolves import specifiers using the TypeScript program from typescript-eslint parser services, so `tsconfig` path aliases (`@lib/*`, `@src/*`) resolve to real files. Returns either a resolved file path or a package name. Unresolvable specifiers are treated as unknown, not as violations.

### 4.4 Rules

Rules are thin: traverse the AST, query `classify`/`resolve`, report. All per-rule logic is small enough to test in isolation.

### 4.5 Presets

- `recommended(options?)`: all five rules at `error`.
- `strict(options?)`: same rules with stricter defaults — `module-boundaries` public entry points default to `index.ts` only. Explicit user options still take precedence in both presets.

## 5. Rules

### 5.1 `layer-dependencies`

Allowed imports per layer:

| From | May import |
|---|---|
| domain | domain |
| application | application, domain |
| infrastructure | infrastructure, application, domain |
| presentation | presentation, application |

Every other pair is a violation, including presentation → domain, presentation → infrastructure, and infrastructure → presentation.

Reports only when both source and target files are classified into known layers and the direction is disallowed.

Options: `layers` — ordered override for alternative layouts.

### 5.2 `domain-framework-free`

In domain-layer files, reports imports of denied packages.

Default deny list: `@nestjs/*`, `typeorm`, `@prisma/*`, `mongoose`, `class-validator`, `class-transformer`, `express`, `fastify`.

Options: `deny` (extends the list), `allow` (exceptions).

Type-only imports are reported too.

### 5.3 `module-boundaries`

A file in module A may import module B only through B's public entry point.

Default public entry points: `index.ts`, `contracts/**`.

Intra-module imports are always allowed. Shared-kernel imports are always allowed.

Options: `publicEntryPoints`.

### 5.4 `aggregate-encapsulation`

Aggregate/entity detection: a class extending a configured base (`AggregateRoot`, `Entity` by default), or any class declared under `domain/**/entities/**`.

Reports:

- public non-`readonly` fields on an aggregate or entity;
- public setters on an aggregate or entity;
- assignments to a property of an aggregate or entity instance from outside its own class, determined by the type checker, not by variable names.

Static factory methods (`create`, `restore`, configurable) on the same class may assign freely.

Options: `baseClasses`, `factoryMethods`.

### 5.5 `immutable-value-objects`

Value object detection: a class extending a configured base (`ValueObject` by default), or any class declared under `domain/**/value-objects/**`.

Reports:

- fields not declared `readonly`;
- assignments to `this.*` outside the constructor;
- methods that mutate `this` instead of returning a new instance.

Options: `baseClasses`.

### 5.6 Message format

Every rule reports a one-line message stating the finding and the fix, followed by the doc link:

```
Domain file imports '@nestjs/common'. Move the dependency behind a port in domain/ports and implement it in infrastructure. See: docs/rules/domain-framework-free.md
```

No autofixes in v0.1; fixes are design decisions.

## 6. Agent integration

### 6.1 Rule docs

`docs/rules/<rule>.md`, each with the fixed sections:

- **What it catches**
- **Why it matters** — stated in consequences, not principles
- **How to fix** — before/after code for each common case
- **When to suppress** — the legitimate exceptions

These docs are the single source for every agent-facing artifact.

### 6.2 `npx eslint-plugin-ddd-guard init`

1. Inspects `src/`, reports which modules and layers the defaults recognize, and writes an ESLint config containing only the deltas from defaults.
2. Writes or refreshes a delimited section in `AGENTS.md` and/or `CLAUDE.md`: layer map, "run lint after changing domain code", "never add `eslint-disable` for ddd-guard rules without asking", links to rule docs.
3. With `--claude-skill`, writes `.claude/skills/ddd-guard/SKILL.md`, generated from the rule docs.

It only ever modifies its own delimited section; re-running replaces that section and never duplicates it. It never touches content outside its markers.

## 7. Error handling

- Invalid plugin options: throw at config build time with the offending key and the expected shape.
- Unclassifiable files and unresolvable imports: silently skipped by design (section 4.2).
- Missing type information for type-aware rules (`aggregate-encapsulation`, `immutable-value-objects`): the rule throws the standard typescript-eslint "parserOptions.project required" error rather than silently doing nothing.
- `init` on a project where no layout is recognized: exits non-zero with a message listing what was scanned and an example config to write by hand.

## 8. Testing and validation

- `layout` and `classify`: table-driven unit tests, no ESLint dependency.
- Each rule: typescript-eslint `RuleTester` with type information, covering both violations and valid cases; the valid cases carry the false-positive protection.
- Fixture projects:
  - `fixtures/domains-style`: `src/domains/*` with `commands/`, `queries/`, `persistence/`.
  - `fixtures/modules-style`: `src/modules/*/{domain,application,infrastructure}`.
  End-to-end tests run the plugin over both.
- Real-world validation before release: run against `Sairyss/domain-driven-hexagon` plus two other public NestJS DDD repositories and the private reference repo. Every hit is triaged as real or false positive; rules are tuned until false positives are near zero. Findings feed the launch write-up.
- Agent demo: the same task given to an agent with and without the plugin; the difference becomes the README headline.
- CI: GitHub Actions running lint, unit tests, rule tests, and fixture end-to-end tests.

## 9. Launch

- npm publish.
- README with a walkthrough GIF of the agent self-correction loop.
- Write-up: "Your agent's code passes tests but breaks your architecture," built on the real-world validation findings.

## 10. Roadmap after v0.1

Conditional on adoption signal:

- `aggregate-reference-by-id` rule.
- Optional Claude Code hook running lint after edits.
- `init` suggesting a config from import-graph inference.
- Reference application (clean-room rewrite of saga, outbox, rules-checker ideas) as the flagship showcase.
- Generators emitting code that passes the rules by construction.
